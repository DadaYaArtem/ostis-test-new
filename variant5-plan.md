# План выполнения варианта 5 расчётной работы (группа из трёх человек)

## 1. Общая стратегия
- Соблюдаем инструкции методички «Расчётная работа по ППОИС (2025)» по установке инструментов (раздел 4.1) и структуре проекта: используем готовые бинарники `sc-machine`, сборку через CMake/Conan, хранение моделей в `knowledge-base`, агентов — в `problem-solver`.
- Перед началом работы фиксируем исходные данные варианта 5: таблицу районов Новосибирска и видов транспорта между ними (пример на стр. ~1550 документа). Чётко отделяем требуемые вычисления: связность, кратчайшие пути, центральность (по эксцентриситету), мосты и диаметр.
- Команда из трёх человек: распределяем ответственность так, чтобы каждый закрывал конкретные deliverables, но промежуточные результаты документировались в Git (`docs/`, `knowledge-base/`, `problem-solver/`).

## 2. Распределение ролей
| Роль | Ответственный | Основные задачи |
| --- | --- | --- |
| **Аналитик/документатор** | Участник A | Сбор и формализация исходных данных (районы, маршруты, виды транспорта), ведение рабочей документации (`docs/variant5/`), описание сценариев использования, оформление отчёта. |
| **Инженер БЗ** | Участник B | Проектирование и наполнение SC-модели транспортной сети в `knowledge-base` (SCn/SCs), подготовка шаблонов для агентов, проверка консистентности через `sc-builder`. |
| **Разработчик решателя** | Участник C | Реализация C++-агентов и утилит, исполняющих требования варианта (DFS, кратчайшие пути, центральность, мосты, диаметр), настройка сборки и тестов. |

## 3. Этапы работ

### Этап 0. Подготовка окружения (день 1)
1. Все участники синхронизируют репозиторий (`git pull rr 0.10.0`), устанавливают зависимости согласно методичке: `sudo apt update && sudo apt install curl ccache python3 python3-pip build-essential ninja-build` и `pip install conan` (разд. 4.1.4–4.1.5).
2. Устанавливаем бинарный `sc-machine 0.10.5` по инструкции (curl → tar → удаление архива и `include`, стр. 322–328). Проверяем наличие `sc-machine/bin/sc-builder`.
3. Настраиваем профили Conan (`conan profile detect`) и проверяем сборку `cmake --preset release && cmake --build --preset release`.
4. А: создает `docs/variant5/requirements.md` с конспектом постановки задачи и допущениями.

### Этап 1. Формализация исходных данных (дни 2–3)
1. А собирает список районов и маршрутов (из методички + реальные данные, если расширяем) и описывает их в табличной форме (район A, район B, вид транспорта, идентификатор маршрута, вес при необходимости).
2. B и C согласуют, какие дополнительные атрибуты нужны (например, весовой коэффициент, частота движения). Решения фиксируются в `docs/variant5/data-schema.md`.
3. А готовит тестовый CSV/JSON и плоский SCs файл с фактами (`knowledge-base/section_variant5/transport_network.scs` шаблон).

### Этап 2. Проектирование и наполнение базы знаний (дни 3–5)
1. B проектирует SC-структуру: классы `district`, `transport_route`, отношения `connects`, тип транспорта, идентификатор маршрута. Использует рекомендации разделов о SC-моделировании (см. главу о базах знаний).
2. Создаёт SCn- или SCs-описание сети, добавляет его в `knowledge-base/section_variant5/`. Проверяет целостность через `./sc-machine/bin/sc-builder -i repo.path -o kb.bin --clear`.
3. При необходимости добавляет осмысленные иерархии (например, `transport_kind` → `tram`, `bus`, `metro`), что упростит запросы агентов.
4. А документирует модель (диаграммы/таблицы) в `docs/variant5/knowledge-base.md`.

### Этап 3. Проектирование решателя (дни 5–6)
1. C совместно с B формирует список агентов/операций:
   - `TransportGraphBuilder` — читает факты из БЗ, строит внутренний граф (списки смежности).
   - `TransportConnectivityAgent` — DFS, выводит компоненты связности и список недоступных районов (требование 2).
   - `AllPairsShortestPathsAgent` — запускает многократный BFS или алгоритм Флойда–Уоршелла (учитывая невзвешенные связи) для пункта 3.
   - `CentralDistrictAgent` — использует матрицу кратчайших расстояний для вычисления эксцентриситета и выбора центра (п. 4).
   - `BridgeDetectionAgent` — алгоритм Тарьяна для мостов (п. 5).
   - `NetworkDiameterAgent` — вычисляет диаметр по матрице кратчайших путей (п. 6).
2. Определяют интерфейсы (ключевые узлы/ключи в `Keynodes.hpp`) и форматы выходных структур (запись результатов в SC-память).
3. Описывают последовательность вызовов в `docs/variant5/solver-design.md` (А помогает оформить).

### Этап 4. Реализация (дни 6–10)
1. C генерирует каркас модуля в `problem-solver/cxx/transport-accessibility-module` (или существующий example-module) и прописывает его в `CMakeLists.txt`/`conanfile.py`.
2. Реализует агентов:
   - Использует `sc-machine::sc-memory` (подключение через `target_link_libraries(... LINK_PUBLIC sc-machine::sc-memory)` как показано в методичке, стр. 631).
   - Добавляет модуль в `SC_EXTENSIONS_DIRECTORY`.
3. Пишет вспомогательные классы: парсер маршрутов из SC-памяти, утилиты графа, сериализация результатов.
4. B помогает тестовыми данными и валидирует, что агенты работают на реальных сегментах сети.
5. Добавляются unit-тесты/скрипты (через `ctest` или Python) для автоматической проверки всех требований.

### Этап 5. Валидация и анализ результатов (дни 11–12)
1. Совместный прогон `./sc-machine/bin/sc-machine -f config` с активированным модулем; собираем логи (`logs/`).
2. Сверяем результаты каждого требования:
   - Связность и список недоступных районов.
   - Матрица кратчайших путей и проверка симметрии.
   - Центральный район и его эксцентриситет.
   - Перечень мостов и комментарии о критичности.
   - Диаметр сети (максимальное расстояние).
3. А оформляет выводы и диаграммы (например, граф визуализирован через `graphviz`).

### Этап 6. Документация и сдача (дни 13–14)
1. А обновляет `README.md` (раздел “Variant 5”), добавляет инструкции по запуску агентов и интерпретации результатов.
2. Финальный отчёт: структура по методичке (цель, задачи, архитектура, результаты вычислений, выводы). Сохраняется в `docs/variant5/report.md`.
3. Все участники делают ревью кода и знаний: `git status`, `git add`, `git commit -m "Implement variant 5 transport accessibility"` и пуш в `rr`.

## 4. Контрольные точки
1. **D1** — окружение готово, есть черновой набор данных.
2. **D3** — БЗ построена, успешно собирается `kb.bin`.
3. **D6** — завершён дизайн агентов, есть утверждённая архитектура решателя.
4. **D10** — реализованы все агенты, проходят тесты.
5. **D12** — получены результаты анализа, подтверждены требования 1–6.
6. **D14** — оформлен отчёт и подготовлен релиз.

## 5. Риски и меры
- **Неоднозначность входных данных**: фиксируем версии таблиц маршрутов в Git, используем формат SCs + CSV.
- **Сложность алгоритмов на больших графах**: тестируем на случайных данных, оптимизируем BFS вместо полного Флойда при больших N.
- **Дублирование знаний и кода**: регулярные синки команды, ревью pull-request’ов.

Следуя этому плану, команда закроет все пункты варианта 5, соблюдёт методические требования и подготовит материалы для сдачи расчётной работы.
